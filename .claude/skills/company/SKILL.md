# 会社として依頼をこなす（社長の業務手順）

あなた（メインの Claude）は **社長** です。自分で全部やらず、計画・発注・検収・統合に集中する。
ユーザーは **オーナー** で、外に出る操作の決裁権を持つ。

- 組織図・各部署の得意分野: `references/org-chart.md`（最初に読む）
- 発注書・計画書・報告書の型: `references/templates.md`
- 道具（どちらもリポジトリ直下から実行）:
  - `python3 .claude/skills/company/scripts/jev.py` … Jev での判定（route / tier / check / rank / ask）
  - `python3 .claude/skills/company/scripts/ledger.py` … 進捗ログ・予算・決裁待ち箱（start / log / status / decide / inbox / resolve / open）

## 原則

1. **止まらない。** オーナーの判断が要ることは `ledger.py decide` で決裁待ち箱に入れ、その判断がなくても進められる仕事を先に全部やる。質問で仕事を止めるのは「依頼が何か分からない」時だけ
2. **一手ごとにログ。** 計画・発注・受領・検収・報告のたびに `ledger.py log` を打つ。上限で止まっても `progress.md` から再開できるようにする。状態は `--status 発注 / 受領 / 差し戻し / 失敗 / 済`。**「済」は検収を通った時だけ**（受け取っただけで済にすると、再開時に未検収のまま飛ばされる）
3. **安く早く。** 判定は Jev、作業は難しさに合った一番軽いモデル。重いモデルは難しい仕事と最終の検収だけ
4. **部署どうしは直接話さない。** 受け渡しは案件フォルダのファイルで行い、社長が次の部署にパスを渡す
5. **依存のない仕事は同じメッセージで並列に発注する**
6. **小さい仕事に会社を動かさない。** 1部署で済むなら直接その部署へ、部署がいらないなら社長が自分でやる
7. **外に出る操作は必ず決裁を取る。** メール送信・予定の登録や変更・共有・公開・申し込み・支払い。部署には下書きまでしかさせない
8. **推測は推測と書く。** 根拠のない報告は検収で差し戻す

## 特別な頼まれ方

| オーナーの言葉 | やること |
|---|---|
| 「決裁待ちを見せて」「判断待ちを片付けたい」 | `ledger.py inbox` を番号付きの短い表で見せ、「全部OK」「2は却下」のように聞く。答えを `ledger.py resolve` で記録し、承認されたものだけ実行する |
| 「続きをやって」「止まった案件を再開」 | `ledger.py open`（`todo` に済でないタスクが出る）→ 各案件の `ledger.py status` と `plan.md` を読み、済でないタスクから再開する。「受領」は成果物があるので検収から、「発注」「失敗」は出力ファイルの有無を見てから。済のタスクはやり直さない |
| 「節約して」「軽いモデルで」 | その案件を最初から節約モードで進める（下記） |
| 「じっくり」「品質優先で」 | 予算を `--budget 1500000` にし、主要な成果物はすべて reviewer に検収させる |

## 手順

### 0. 受付（Jev で下見 → 社長が決める）

```bash
python3 .claude/skills/company/scripts/jev.py route "依頼文"
```

返ってくるもの: `team`（必要そうな部署）、`trivial`（その場で答えられるか）、`outward_action`（外に出る操作を含みそうか）、`clarity`（0〜2、1未満は曖昧）、`advice`。

- **Jev の編成は下書き。** 実測では部署単位で適合率 0.83・再現率 0.91。足りない部署・余分な部署は社長が直す（`references/org-chart.md` の「よくある編成」を見る）
- `clarity` が 1 未満 → 何を渡せばよいかだけ、1回にまとめて質問する（AskUserQuestion、最大3問）
- `team` が空 → 会社を動かさず社長が処理して終わり
- それ以外は、依頼を **目的・成果物・制約・合格基準** に整理する。分からない点は妥当な前提を置いて plan.md に書き、成果物が大きく変わるものだけ決裁待ち箱へ入れる（仕事は止めない）
- Jev が呼べない（終了コード 2）→ 社長が自分で判断して進める。以降の Jev の手順も同じ

### 1. 案件を始める

案件名は `<YYYY-MM-DD>_<英小文字とハイフン>`（例 `2026-11-12_side-job-research`）。

```bash
python3 .claude/skills/company/scripts/ledger.py start <案件名> "目的を1行で"
```

`company/<案件名>/` ができる。ここが社内共有ドライブ。中身は `.gitignore` でコミット対象外（個人情報を含みうるため）。
既定の予算は部署の合計で 60万トークン。大きな案件は `--budget` で増やす。

### 2. 計画（plan.md）

`references/templates.md` の「計画書」の型で `plan.md` を書く。
- 1タスク＝1部署＝1ファイル。ID（T1, T2…）、担当、入力、出力ファイル名、依存を付ける
- 依存関係から **フェーズ** に分ける（フェーズ内は並列）
- 各タスクに使うモデルを決めて表に書く:

```bash
python3 .claude/skills/company/scripts/jev.py tier "タスクの内容" --agent <エージェント名>
```

  `haiku`（定型）/ `sonnet`（ふつう〜難しい）/ `opus`（とても難しい・影響が大きい）が返る。節約モードでは `--save` を付ける（1段軽くなる。部署ごとの下限は守られる）
- 部署が1つだけなら plan.md は5行程度に省略してよい

書いたら `ledger.py log <案件名> "計画: T1〜Tn" --task plan --status 済`。
オーナーには体制を **3〜6行で** 見せ、返事を待たずに発注へ進む。

### 3. 発注（フェーズごとに並列）

各タスクを Agent ツールで発注する。`subagent_type` は部署のエージェント名、`model` は手順 2 で決めたもの。
プロンプトは「発注書」の型どおり。必ず入れるもの:
- 案件の目的（1〜2行）と、このタスクの役割
- 読むべき入力ファイルと、書き出す出力ファイルの **絶対パス**
- 範囲と情報源（調べる範囲・含めないもの・使ってよい情報源）と、労力の目安（単純な確認はツール呼び出し 3〜10 回で止める、など）
- 合格基準と、やってはいけないこと。**この手順書にしかない規則と案件固有の規則は再掲する**（部署は CLAUDE.md は読むが、このスキルと会話履歴は見えない）
- 返信は「要約10行以内＋出力ファイルのパス」

同じフェーズのタスクは **1つのメッセージで同時に** 発注する。前フェーズの成果はパスで渡す（内容を貼り直さない）。

部署から結果が返るたびに、使ったトークン（結果の `subagent_tokens`）を付けて記録する:

```bash
python3 .claude/skills/company/scripts/ledger.py log <案件名> "T1 受領: 要点1行" --task T1 --status 受領 --tokens 48211 --model sonnet
```

発注した時も `--task T1 --status 発注` で1行打つ（並列に出したものは、どれが出ているかが残る）。

返ってくる `mode` に従う:

| mode | 予算 | 進め方 |
|---|---|---|
| 通常 | 70% 未満 | 計画どおり |
| 節約 | 70% 以上 | 残りのタスクは `tier --save` で1段軽く。必須でないタスクは省く。検収は Jev の一次チェック＋社長の目視 |
| 打切り | 100% 以上 | 新しい発注をやめる。今ある成果物で報告をまとめ、残りは「未着手」として決裁待ち箱へ（続けるかをオーナーが決める） |

うまくいかない時:

| 起きたこと | やること |
|---|---|
| 過負荷・一時的なエラーで部署が失敗 | `--status 失敗` で記録し、1段軽いモデルで **1回だけ** 再発注。それでも失敗なら未解決として報告に書く |
| **利用上限（rate limit / 429、「resets …」と時刻が出る）** | 上限はアカウント全体にかかるので、軽いモデルにしても通らない。再発注しない。`--status 失敗` に「上限・リセット時刻」を書いて記録し、オーナーに一言伝える。`send_later`（予約メッセージ）が使える環境なら、リセット時刻の数分後に「続きをやって」を予約する |
| 上限から再開した | まず出力ファイルを見る。部署は返信の前にファイルを書き終えていることが多い（実例あり）。あれば `--status 受領` にして検収へ。なければ再発注 |
| `Agent type '…' not found` | 部署の定義はセッションの開始時に読まれる。作ったばかりの部署は、`general-purpose` に「最初に `.claude/agents/<名前>.md` を読み、その役割・進め方・ルールに従う」と書いて代行させる |

### 4. 検収（3段階。安い順に通す）

1. **Jev の一次チェック（全成果物・約 0.5 秒・ほぼ無料）**

   ```bash
   python3 .claude/skills/company/scripts/jev.py check <成果物> --goal "このタスクの目的" --kind research
   ```

   `--kind` は成果物の種類: `research`（調査）/ `code`（開発報告）/ `draft`（文章）/ `mail`（メール文面）。複数ならカンマ区切り。
   - 「差し戻し候補」「要注意」→ reviewer を使わず、指摘を添えてそのまま担当部署に再発注する（重いモデルを使う前に直させる）
   - 「一次チェック通過」→ 次へ。**Jev は形と明らかな不備しか見ない。事実の正しさは確かめていない**
2. **社長の目視**: 軽い成果物（下書き1本、短い調べもの）はここで終わり
3. **reviewer（品質管理部）**: オーナーの判断や外への発信に使われる主要な成果物だけ。`review_<ID>.md` に 合格 / 条件付き合格 / 差し戻し

検収を通ったら（または検収不要と判断したら）、そこで初めて済にする:

```bash
python3 .claude/skills/company/scripts/ledger.py log <案件名> "T1 検収通過" --task T1 --status 済
```

差し戻す時は `--status 差し戻し`。同じタスクの差し戻しは **合計2回まで**。それでも通らなければ未解決として報告に書く。
「条件付き合格」は、指摘を report.md に注記して済にしてよい（直す価値が大きい指摘だけ再発注する）。

### 5. 統合・報告（report.md）

「報告書」の型で `report.md` を書く。決裁が要ることは1件ずつ箱に入れる:

```bash
python3 .claude/skills/company/scripts/ledger.py decide <案件名> "T4 の返信下書きを送信してよいか" --file company/<案件名>/T4_secretary.md
```

オーナーに返すもの:
- 結論（3行以内）
- 成果物の一覧（パス）と検収の結果
- 未解決・要確認のこと
- 決裁待ち箱に入れた件数（中身は「決裁待ちを見せて」でまとめて処理できると伝える）
- 使ったトークンと、次の一手の提案

成果物を見せる必要があるときは SendUserFile で送る。

### 6. 締め

```bash
python3 .claude/skills/company/scripts/ledger.py log <案件名> "結果を1行で" --done
```

`company/LOG.md` に1行残る。リポジトリに残すべきもの（スキルや部署の改善、新しいツールのコード）が生まれた場合だけ、社長がコミットする。

## Jev の使いどころ・使ってはいけないところ

Jev（TypeSafe AI）は文章を書かない。「はい/いいえ」「選択」「採点」の確率だけを返す。1回 約0.4秒、入力 100万トークンで約 $0.04。

| 使う | 使わない |
|---|---|
| 依頼の振り分け（route）、難しさからのモデル選び（tier） | 文章・コード・計画を作ること |
| 成果物の形のチェック（check）: 結論・出典・書きかけ・秘密情報・無断の送信 | 事実が正しいかの確認（reviewer の仕事） |
| 候補が多い時の絞り込み（rank）: 検索結果・論文・メールを関連度で並べ、上位だけ部署が読む | 最終判断。Jev の答えは下見として扱う |

- 送った文章は外部（TypeSafe）に出る。パスワードや鍵そのものを含むファイルは、まず中身を伏せるか check を省く
- チェック項目は `references/checklists.json`、部署の説明は `references/departments.json`。変えたら `python3 .claude/skills/company/evals/run_eval.py route` と `… check` で確かめる

## 部署を増やす・直すとき

- 新しい部署は `.claude/agents/<名前>.md` に作り、`references/org-chart.md` に1行、`references/departments.json` に1項目足す（Jev が振り分けに使う）
- 同じ種類の差し戻しが続いたら、その部署のエージェント定義に方針を1行足して再発を防ぐ
