# company スキル改善提案書

## 結論（3行以内）
- 最優先は2つ。①「受領」を記録しただけで「済」になる仕組みを直す（検収前に再開対象から外れる）。②発注書に「情報源・範囲」「労力の目安」「再掲する規則」を足す。
- 次に、reviewer の依頼文を「基準に照らして正しさに影響する抜けだけ」に改め、権限制限の裏打ちを検討する。
- 提案は5つ。どれもファイル数行の変更で済む。反映するかはオーナーの決裁事項。

## 提案1：受領と完了（済）を分ける
**①問題**
- SKILL.md 手順3の例 `ledger.py log <案件名> "T1 受領: 要点1行" --task T1 --tokens ...` は `--status` を付けていない。ledger.py の既定は `済`（scripts/ledger.py 188行目）。
- つまり成果物を受け取った時点で「済」になる。検収前・差し戻し中でも済と記録される。
- 一方、SKILL.md「続きをやって」の行は「『済』でないタスクから再開」「済のタスクはやり直さない」と書く。中断すると、未検収のタスクが再開時に飛ばされる。

**②変更案**
- SKILL.md 手順3の例を `... --task T1 --status 途中` に変える。
- 手順4の末尾に追記：「検収を通った（または検収不要と判断した）時点で `ledger.py log <案件名> "T1 検収通過" --task T1 --status 済` を打つ。**済にするのは検収後だけ。**」

**③根拠**
- T1 §1「早すぎる『完了』宣言」：機能一覧は最初すべて未達にし、テスト後にだけ「達成」に変える。https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- T1 §4：再開時は進捗ファイルを読み、未完の最優先から再開する（同上）。
**④効果：大／手間：小**（文面2か所。ledger.py は変えない）

## 提案2：発注書に「情報源・範囲」「労力の目安」「再掲する規則」を足す
**①問題**
- templates.md「発注書」は【案件】【担当】【入力】【出力】【合格基準】【やってはいけないこと】【返信】のみ。
- 調べる範囲・使う情報源・どれくらい深追いするかの欄がない。SKILL.md 手順3の「必ず入れるもの」にもない。
- 守らせたい規則は「送信・登録・公開…／根拠のない断定」の2行だけ。サブエージェントは CLAUDE.md 全体を見られない。

**②変更案**（templates.md の発注書に追加）
```text
【範囲と情報源】<調べる範囲／含めないもの／使ってよい情報源・ツール>
【労力の目安】<例: 単純な確認＝ツール呼び出し3〜10回で止める／複雑な調査＝小問ごとに深掘り>
【守る規則】<このタスクに関係する規則を再掲。例: 個人情報を検索語に入れない>
```
SKILL.md 手順3「必ず入れるもの」に同3項目を1行ずつ追記。

**③根拠**
- T1 §1「文脈の欠落」：サブエージェントは会話履歴を見ず、CLAUDE.md 全体も見えない。規則は発注プロンプトで再掲する。https://code.claude.com/docs/en/sub-agents
- T1 §1「曖昧な発注による重複作業」「労力の過剰投入」：目的・出力形式・情報源・タスクの境界を明示し、複雑さに応じた労力の目安を書く。https://www.anthropic.com/engineering/multi-agent-research-system
- T1 §2：具体的なプロンプトは不要な広域探索を避ける（https://code.claude.com/docs/en/costs ）。

**④効果：大／手間：小**

## 提案3：reviewer の依頼文を「基準照合・正しさ優先」にする
**①問題**
- reviewer.md の description は「厳しくチェックし」、本文は「問題を見つけて指摘するのが仕事」。
- 「問題を探せ」型の指示は、必ず何かを見つけて過剰な修正を生む（T1 §3）。reviewer.md には除外の指示（スタイルは対象外など）がなく、軽微な指摘も拾う作りになっている。

**②変更案**（reviewer.md 本文の冒頭を差し替え）
```text
あなたは品質管理部の検収担当です。plan.md の合格基準を基準に、各要件が満たされているかと、
正しさに影響する抜け・誤りだけを報告します。文体・好みの問題は除外します。
問題が見つからなければ「見つからなかった」と書いてよい（無理に探さない）。
```
「判定の目安」の「軽微な指摘」は残してよいが、「軽微＝正しさに影響しないもの。原則書かない」と一言足す。

**③根拠**
- T1 §3「依頼文の作り方」：仕様を基準に、正しさに影響する抜けだけ報告、スタイルは除外。「問題を探せ」と言うと過剰な修正を生む。https://code.claude.com/docs/en/best-practices

**④効果：中／手間：小**

## 提案4：reviewer の「編集しない」を仕組みで裏打ちする
**①問題**
- reviewer.md の tools は `Read, Write, Glob, Grep, Bash, WebSearch, WebFetch`。「成果物のファイルは編集しない」はプロンプト上の約束だけで、Write と Bash があれば技術的には書き換えられる。
- review_<ID>.md を書くために Write は要る。そのため「Edit/Write を外す」ことはできない。

**②変更案**（案。どれを採るかは要検討）
- 案A：小さい手間で。tools から Bash を外す（Jev の一次チェックは社長側で先に走らせ、結果を発注書に貼る）。
- 案B：hook で成果物への書き込みを拒否し、review_*.md だけ許可する（プロンプトの禁止は第一防衛、hook はバックストップ）。
- 【要確認：hook の具体的な設定書式。T1 は考え方（exit code 2 でブロック）までで、設定例は未取得】

**③根拠**
- T1 §3「レビュー役の置き方」：読み取り専用のレビュー役を置く。制限は依頼ではなく Claude Code が強制する。https://code.claude.com/docs/en/best-practices
- T1 §5：hooks で細かく制御できる。プロンプトの禁止指示は第一防衛、hook はバックストップ。https://code.claude.com/docs/en/sub-agents

**④効果：中／手間：中**（実際の被害は未発生。保険の位置づけ）

## 提案5：部署定義に上限（maxTurns）と子生成の注記を足す
**①問題**
- `.claude/agents/` の8ファイルのどれにも `maxTurns` がない。1体が長引いた場合の上限がトークン予算（社長側の事後集計）だけになる。
- `paper-researcher.md` の tools に `Agent` がある（pubmed-survey/SKILL.md が採点を Agent で並列起動する設計）。一方、SKILL.md 原則4「部署どうしは直接話さない」と org-chart.md には、子を生成することの記載がない。
- engineer.md の description には「使わない場面」がない（web-researcher.md にはある）。

**②変更案**
- 各 .md のフロントマターに `maxTurns: <数>` を足す。【要確認：適切な数値。T1 に目安なし。まず web-researcher / writer で試す】
- org-chart.md の paper-researcher 行に「内部で子エージェントを並列起動する（トークンを多く使う）」と注記。【要確認：子のトークンが ledger.py の `subagent_tokens` に含まれるか】
- engineer.md の description に「文章の執筆・事実調査は writer / web-researcher に任せる」を足す。

**③根拠**
- T1 §5：maxTurns は上限到達で部分結果と印が付く。ネストは既定で最大3階層、`Agent` を tools から外すと禁止できる。https://code.claude.com/docs/en/sub-agents
- T1 §1「役割の曖昧さ」：description を1つに絞る（同 Best practices 節）。T1「照合メモ」：maxTurns と境界は追加余地あり（推測）。

**④効果：小／手間：小**

## すでに対応済み（提案に含めない）
- 発注書に目的・入出力の絶対パス・合格基準・禁止事項を入れる（templates.md、SKILL.md 手順3）。
- 返信を「要約10行以内＋ファイルパス」に絞り、部署間はファイル経由で受け渡す（原則4・手順3）。T1 §1・§2 の方針と一致。
- 作業ごとのモデル選び（`tier`）と、発注時の `model` 指定。節約・打切りモードで予算を管理する（手順2・3）。
- 依存のない仕事の並列発注、小さい仕事に会社を動かさない（原則5・6）。進捗ログと再開の手順（原則2。済の付け方は提案1）。
- 別部署（reviewer）による検収、安い順の3段階、差し戻し合計2回の上限（手順4。T1 §3 の停止条件の原則と合致）。
- 部署定義のフロントマター（name / description / tools / model）と tools の絞り込み。
